# Dependency updates

Dependabot opens pull requests once a week for the crates in `server/`, the packages in `client/`, the inputs in `flake.lock` and the GitHub actions, as [`.github/dependabot.yml`](../../.github/dependabot.yml) configures. Minor and patch updates come grouped. Each update waits seven days after its release. Dependabot opens its pull requests ready for review, so they run every CI job.

An update of `flake.lock` can bring new versions of Rust, pnpm, `editorconfig-checker`, `cargo-deny` or `cargo-about`. The lint checks that compare the pins for work without Nix then fail and name the version of nixpkgs. A new pnpm also changes the hash of the client dependencies, and the build names the new one. Push one commit to the Dependabot branch that sets `channel` in `server/rust-toolchain.toml`, `packageManager` and `EC_VERSION` in `client/package.json`, the hash in `client/pnpm-deps.hash` and the versions of `cargo-deny` and `cargo-about` under [Tests and lints](../../CONTRIBUTING.md#tests-and-lints) to those versions, together with fixes for new Clippy lints. Dependabot no longer rebases a branch with commits of someone else. If `main` moves before the merge, rebase the branch by hand or comment `@dependabot recreate`, which drops your commit. Dependabot moves only the revisions in `flake.lock`. Change the branch of `nixpkgs` and the tag of `crane` in `flake.nix` by hand.

[`client/pnpm-workspace.yaml`](../../client/pnpm-workspace.yaml) lets pnpm install only releases older than seven days, also those already in `pnpm-lock.yaml`. Only the packages under `allowBuilds` may run build scripts, and pnpm fails on a new package with a build script until it gets an entry there. To take a security fix younger than seven days, add its exact version to `minimumReleaseAgeExclude`, such as `picomatch@4.0.8`, then update it. `pnpm update` also moves a package that comes in through another one, as long as the fixed version fits the range that the other package requires. Remove the entry once the release is older than seven days. A version update whose fetch fails on a young release waits instead. Comment `@dependabot recreate` once the release is old enough.

```sh
cd client
pnpm update <package>
```

If the fix lies outside that range, pin it under `overrides` in `client/pnpm-workspace.yaml`.

The Nix build fetches the client dependencies once for `pnpm-lock.yaml` and checks them against the hash in [`client/pnpm-deps.hash`](../../client/pnpm-deps.hash). Every change of `pnpm-lock.yaml` or `pnpm-workspace.yaml` makes the build fetch the dependencies anew, which also checks the release age. If the fetched packages differ, the build fails with `got: sha256-…`. Write that value to the file. Without Nix, the job `build` of CI shows the same error. On pull requests of Dependabot, the workflow [`client-dependencies`](../../.github/workflows/client-dependencies.yaml) writes the hash and pushes it with the token of the GitHub App `adunata-client-dependencies`, so the push starts CI on the pull request. It writes the hash only in runs that Dependabot starts, because only those see the secrets of the App. After a push of someone else, the workflow names the hash in a notice, and that person writes it to the file. `[dependabot skip]` in its message lets Dependabot keep rebasing the branch.

The workflow [`advisories`](../../.github/workflows/advisories.yaml) checks both lock files against the advisory databases every day and on pull requests that change them. It fails on any advisory of a crate and on an advisory of a client package of severity high or critical. If such an advisory has no fix yet, add it to `client/audit-exceptions.json` with its GHSA ID, the reason and an expiry date. The run fails once the date has passed and, outside pull requests, once the exception matches no advisory. GitHub notifies only the person who last changed the schedule of a failed scheduled run, so check the workflow in the Actions tab. For a crate, add `{ id, reason }` to `ignore` under `[advisories]` in `server/deny.toml`.
